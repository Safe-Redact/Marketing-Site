# SafeRedact Blog Architecture

## Decision

Phase 4A uses Decap CMS with Git-managed Markdown. The existing Next.js marketing repository remains the only public website. There is no database, separate public application, paid CMS subscription, MDX execution, or visitor-comment system in this phase.

The content studio shell is served at `/admin`, but live staff authentication and publishing are not complete until an approved GitHub OAuth path is configured and tested. The studio is not linked from public navigation, is excluded by robots rules, and contains no secret or write credential.

## Implemented system

```text
Public visitor
  -> Next.js routes
     -> content/blog/*.md (validated at the server/build boundary)
     -> public/images/blog/* (local, approved media only)

Authorized editor (after OAuth configuration)
  -> /admin/index.html (Decap CMS)
  -> GitHub OAuth service
  -> editorial-workflow branch + pull request
  -> reviewed merge to master
  -> deployment rebuild publishes eligible content
```

Public routes:

- `/blog`: featured article, search, categories, pagination, and an honest empty state.
- `/blog/[slug]`: published article body, metadata, structured data, and related articles.
- `/blog/category/[slug]`: category archive with pagination.
- `/admin`: noindexed redirect to the static Decap shell at `/admin/index.html`.

## Content eligibility boundary

All Markdown files are parsed through one strict loader in `src/lib/blog/content.ts`. A public article must:

1. Pass the exact frontmatter schema.
2. Have a safe kebab-case slug matching its filename.
3. Have `status: published`.
4. Have a publication date that is not in the future.
5. Contain no raw HTML.
6. Use only safe links and local `/images/blog/` image paths.
7. Provide alt text for every content or featured image.

Draft, future-dated, archived, missing, malformed, and traversal-like article requests are excluded. The same published loader feeds pages and the sitemap so discoverability cannot bypass route eligibility.

## Security boundaries

- Markdown, not MDX, is used. Article content cannot execute JavaScript or React components.
- `react-markdown` renders with HTML skipped; the pre-render validator rejects raw HTML before rendering.
- Frontmatter is validated with Zod and rejects unknown fields.
- Article slugs are allowlisted rather than interpolated into file paths.
- Only local blog image paths are accepted; remote editor-supplied image URLs are rejected.
- External links receive `noopener noreferrer` when opened in a new tab.
- Generated Decap configuration contains public repository, branch, site, scope, and broker coordinates only, never OAuth secrets. Its reviewed schema is provider-neutral and missing authentication settings fail closed to reserved `.invalid` origins.
- `/admin` is absent from navigation and sitemap and is disallowed in `robots.txt`; this is discoverability hygiene, not authentication.
- GitHub authorization must enforce staff identity and repository permissions before the studio is production-enabled.

## Git and publishing model

The verified remote is `https://github.com/Safe-Redact/Marketing-Site.git`. Git reports `master` as `origin/HEAD`; both `origin/master` and `origin/main` exist at the legacy baseline. Decap therefore targets `master` explicitly, not the current feature branch.

`publish_mode: editorial_workflow` is configured. After OAuth is enabled, unpublished entries are expected to use Decap's GitHub editorial workflow and pull requests. Repository branch protection and required human review remain external operational requirements. No Git history operation or deployment was performed during implementation.

## Authentication status

Decap's GitHub backend requires an OAuth authentication service (or an explicitly approved hosted equivalent). None exists in this repository and none was invented. Consequently:

- the studio shell is implemented;
- its content model and Git target are implemented;
- staff login is **not verified**;
- authenticated editing and live publishing are **not operationally accepted**.

See `PHASE5_DESIGN_SPEC.md`, `DECAP_NETLIFY_AUTH_PLAN.md`, and `DECAP_CMS_SETUP.md` for the provider-neutral launch gate.

## Deployment assumptions

The host must support the existing Next.js 15 application, static files under `public/`, production builds triggered by reviewed Git changes, and redirects generated by the App Router. The selected OAuth service must use HTTPS, an allowlisted callback, server-held client secret, and least-privilege repository authorization.

Because publishing changes Git content, each approved merge requires a new deployment build unless the eventual host provides an equivalent safe rebuild hook. No deployment provider is assumed by source code.

## Phase boundary

Visitor comments, replies, reports, custom moderation, visitor identity, rate limiting, anti-spam, and comment persistence are Phase 4B work. They must not be stored in the article Markdown files. A future discussion store should be independently replaceable and should reference immutable article slugs or dedicated article IDs without changing the Git-backed article repository.
